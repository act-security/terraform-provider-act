# act_notification_recipient (Resource)

A tenant-wide recipient group for notification rules: a name and up to 100 members, which are Act users, email addresses and Slack channels. Rules reference it in `recipient_ids`. Notification rules are in preview; the tenant needs them enabled.

A recipient has up to 100 members across `user_ids`, `emails` and `slack_channel` blocks, and at least one.

An Act user gets alerts through the receiver they chose in their Act profile, email or Slack. Terraform doesn't manage that choice. When a user leaves the tenant, they stay a member with `in_tenant = false` in `members`, receive nothing, and the provider warns until you remove them from `user_ids`.

## Example Usage

```terraform
data "act_user" "lee" {
  email = "lee@example.com"
}

resource "act_notification_recipient" "platform" {
  name     = "Platform team"
  user_ids = [data.act_user.lee.id]
  emails   = ["platform@example.com"]

  slack_channel {
    integration_id = act_slack_integration.this.id
    channel_id     = "C05PLATGRD2"
  }
}
```

Reference it from a rule's `recipient_ids` with its `id`, so Terraform deletes the rule's reference before the recipient. Act refuses to delete a recipient while any rule names it, and the error lists those rules.

Act sorts members, so a plan never shows a change for their order. Email addresses must be lowercase.

When Act adds member types this provider version does not know, `min_client_revision` goes above 1. The provider then warns and refuses to update the recipient, so it never drops members it cannot see.

## Schema

### Required

- `name` (String) The name Act shows, up to 100 characters. Unique in the tenant.

### Optional

- `emails` (Set of String) Email addresses, in lowercase.
- `slack_channel` (Block Set) A Slack channel. Repeat the block for more channels; they may come from different Slack integrations. (see [below for nested schema](#nestedblock--slack_channel))
- `user_ids` (Set of String) Act users of this tenant, from the `act_user` data source. Each user gets alerts through the receiver they chose in their Act profile (email or Slack), which Terraform does not manage.

### Read-Only

- `created_via` (String) Where the recipient was created: `terraform`, `api` or `ui`.
- `id` (String) The recipient ID.
- `last_modified_via` (String) Where the recipient last changed: `terraform`, `api` or `ui`.
- `members` (Attributes List) Every member as Act reports it, with the user names and channel names Act resolved. `in_tenant` is false for a user who has left the tenant; such a member receives nothing. (see [below for nested schema](#nestedatt--members))
- `min_client_revision` (Number) The oldest client revision that can show every member. This provider understands revision 1 and refuses to update a recipient that needs a newer one, so it never drops members it cannot see.
- `revision` (Number) The recipient's revision in Act. It goes up on every change.
- `rule_ids` (Set of String) The notification rules that reference this recipient. Act refuses to delete a recipient while any rule does.
